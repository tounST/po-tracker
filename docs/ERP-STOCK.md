## 1. ภาพรวม — ERP คืออะไรในโปรเจคนี้

ERP **ไม่ได้แทนที่** PO Tracker แต่เป็น **"เมนูใหญ่"** ที่ครอบอยู่ข้างบน และ PO Tracker เป็น 1 หมวดในนั้น

```
tounst.github.io/po-tracker/
├── index.html        ← router เดิม (คนงานเข้าหน้านี้ → PO Tracker)  ❗ห้ามแตะ
├── po-mobile.html    ← PO Tracker มือถือ (คนงาน)                    ❗ห้ามแตะโดยไม่จำเป็น
├── po-desktop.html   ← PO Tracker PC                                ❗ห้ามแตะโดยไม่จำเป็น
├── erp.html          ← 🆕 ERP Dashboard (ออฟฟิศ)
└── stock.html        ← 🆕 คลังสต๊อก
```

**ทางเข้า** (ต้องพิมพ์ใน address bar ของเบราว์เซอร์ ไม่ใช่ช่องค้นหาใน GitHub):

| ใคร | URL |
|---|---|
| ออฟฟิศ / toun | `https://tounst.github.io/po-tracker/erp.html` |
| คลังสต๊อก | `https://tounst.github.io/po-tracker/stock.html` |
| คนงาน | `https://tounst.github.io/po-tracker/po-mobile.html` (เดิม ไม่เปลี่ยน) |

**หลักการแยกส่วน:** ERP → กดเข้า PO ได้ แต่ PO → ไม่มีลิงก์กลับมา ERP
คนงานจึงไม่มีทางเจอ ERP · PWA ของคนงานยังผูกกับ `po-mobile.html` เหมือนเดิม

## 3. ฐานข้อมูล (Supabase `rkdxbxtakvisroxelrvq`)

### ตารางใหม่

| ตาราง | หน้าที่ |
|---|---|
| `stock_items` | วัสดุ — name, category, unit, qty_current, **qty_min** (ห้ามต่ำกว่า), **qty_target** (ค่ากลาง), cost_per_unit (เฉลี่ยเคลื่อนที่), source_country, ministry_seq, is_active |
| `stock_movements` | **ประวัติทุกการเคลื่อนไหว** — item_id, movement_type, qty, balance_after, **unit_cost**, ref_type/ref_id, **doc_no/supplier/photo_url**, **reverses_id**, created_by |

`movement_type` = `in` \| `out` \| `adjust` \| `initial` (มี CHECK constraint — **เพิ่มค่าใหม่ต้อง migrate ก่อน**)

⚠️ **`qty` ของ `adjust` เก็บ "ยอดใหม่แบบสัมบูรณ์" ไม่ใช่ส่วนต่าง**
เวลาอ่านย้อนหลังต้องคำนวณส่วนต่างจาก `balance_after` chain เท่านั้น (เคยพลาดมาแล้ว → BUG34)

### Functions (สำคัญมาก — ห้ามเขียน stock ตรง ๆ)

| Function | ทำอะไร |
|---|---|
| `apply_stock_movement(item, type, qty, unit_cost, po, note, by, doc_no, supplier, photo_url)` | ล็อกแถววัสดุ (`FOR UPDATE`) → เขียน ledger + คำนวณเฉลี่ยเคลื่อนที่ + อัปเดตยอด **ในทรานแซกชันเดียว** |
| `reverse_stock_movement(movement_id, note, by)` | ออกรายการกลับ ผูก `reverses_id` · กันยกเลิกซ้ำ/ยกเลิกรายการยกเลิก |

> ❗ **ห้ามกลับไป `insert` + `update` จากฝั่ง client เด็ดขาด** — นั่นคือสาเหตุ BUG32 (ยอดหายเมื่อสองคนกดพร้อมกัน)

### Storage
bucket `stock-docs` — public read, 5 MB, เฉพาะรูป
รูปถูกย่อฝั่ง client เป็นด้านยาว 1400px / JPEG q0.72 (~200 KB) ก่อนอัปโหลด

### สิทธิ์ใหม่ใน `role_permissions`
`stockIn` · `stockOut` · `stockAdjust` · `stockReverse` · `viewStockDocs`
**ค่าเริ่มต้น: admin = true, ที่เหลือ = false** · toun เปิดให้คนอื่นเองได้ที่แท็บ 🔐 สิทธิ์ ใน stock.html

Free tier จะ **auto-pause เมื่อไม่มีใครใช้** (เจอจริงตอน 30 ก.ค. — เงียบไป 3 เดือนแล้วหลับ)

## 6. Decision log — ทำไมถึงเลือกแบบนี้

**ต้นทุนเฉลี่ยเคลื่อนที่ ไม่ใช่ FIFO**
สี/ทินเนอร์เทรวมถังกัน แยกไม่ออกว่าลิตรไหนมาจากล็อตไหน FIFO layers จึงไม่ตรงกับของจริงและซับซ้อนกว่าโดยไม่ได้ประโยชน์เพิ่ม

**ตีตราราคาลงทุกรายการ (`unit_cost`)**
เดิมมูลค่าคิดจาก `qty × cost_per_unit` ซึ่งเป็นช่องเดียวที่แก้ได้ → พอซื้อของแพงขึ้นแล้วอัปเดตราคา **มูลค่าของเดือนที่ผ่านไปแล้วก็เปลี่ยนตาม** ประวัติจึงเชื่อถือไม่ได้ พอตีตราแล้ว การอ่านย้อนหลังก็แค่บวกเลข = ถูกต้องขึ้นและเร็วขึ้นพร้อมกัน

**ใช้ `ref_type`/`ref_id` เดิม แทนการเพิ่ม `po_number`**
ตอนจะเพิ่มคอลัมน์พบว่าตารางมี polymorphic pair อยู่แล้ว → ใช้ของเดิม (`ref_type='po'`) ไม่สร้างคอลัมน์ซ้ำซ้อน

**ปรับยอดในรายงานกระทรวงถูกรวมเข้า "ปริมาณที่ใช้"**
ฟอร์มไม่มีช่องปรับยอด แต่บังคับ `ยอดยกมา + รับ − ใช้ = คงเหลือ` ถ้าไม่รวมจะส่งไม่ผ่าน
ของที่นับขาด = ของหายไปจริง → รายงานเป็นการใช้ แล้วเขียนกำกับในช่องหมายเหตุ

**ห้ามใช้ `qty` ของ adjust เป็นส่วนต่าง**
`adjust` เก็บยอดใหม่แบบสัมบูรณ์ (UI ก็เขียนว่า "ยอดคงเหลือใหม่") ถ้าอ่านเป็นส่วนต่าง การนับสต๊อกจะกลายเป็นการซื้อเข้า → ต้องคำนวณจาก `balance_after` chain เสมอ

**สิทธิ์ของ admin ล็อก 3 ชั้น**
UI disabled + `savePerm` ปฏิเสธ + `loadRolePermissions` ไม่สนใจแถว admin
ถ้า admin ปิดสิทธิ์ตัวเองได้จะไม่มีทางกลับเข้าไปแก้ นอกจากงัด DB

## 7. คำแนะนำเชิงธุรกิจที่ให้ไว้แล้ว (toun ยังไม่ตัดสินใจ)

### บาร์โค้ด — **ยังไม่ควรซื้อ**
- SKU แค่ 15 รายการ · ถังสีไม่มีบาร์โค้ดที่ใช้ได้ · สีเบิกแบบ "ตัก" ไม่ใช่ "หยิบชิ้น" → ยิงแล้วยังต้องพิมพ์จำนวนอยู่ดี
- **ทางที่ดีกว่า:** พิมพ์ **QR ติดที่ชั้นวาง** (ไม่ใช่ที่ถัง — ถังหมดแล้วทิ้ง QR หายไปด้วย) ส่องด้วยกล้องมือถือที่มีอยู่ ต้นทุน ~50 บาท
- เกร็ด: เครื่องยิงบาร์โค้ดทำงานเหมือน**คีย์บอร์ด** ถ้าวันหน้าซื้อมา ระบบปัจจุบันรองรับได้เลยแค่เพิ่มช่องค้นหา

### แอปถ่ายรูปอ่านตัวเลข (OCR) — **ควรทำ แต่ไม่ใช่อันแรก**
- **เป้าหมายแรกควรเป็น "ใบส่งของที่พิมพ์มา"** ไม่ใช่ลายมือช่าง (พิมพ์ = อ่านแม่น, ลายมือเปื้อนสี = เสี่ยง)
- ความเสี่ยงหลักคือ **"ผิดแบบเงียบ"** — อ่าน `-13` เป็น `-18` ไม่มีอะไรดูผิดแต่สต๊อกเพี้ยน 6,500 บาท → ต้องมีหน้าจอยืนยันทุกครั้ง
- **เคล็ดลับ:** ออกแบบฟอร์มกระดาษเองแล้วพิมพ์แจก (พิมพ์ชื่อวัสดุไว้ล่วงหน้า ช่างเขียนแค่ตัวเลขในช่อง) → ความแม่นกระโดดขึ้นมาก
- ค่า AI อ่านภาพ < 1 บาท/ภาพ ≈ 30 บาท/เดือน · เวลาพัฒนา ~1-2 สัปดาห์

### เครื่องชั่งผสมสีต่อคอม — **อย่าซื้อเพื่อเอาข้อมูล**
- ถ้าเหตุผลคือ "ให้ระบบได้ข้อมูลอัตโนมัติ" → ไม่คุ้มชัดเจน
- **แต่ผู้ผลิตสีมักให้ยืม/แถม** แลกกับการซื้อสีแบรนด์เขา → **โทรถามตัวแทน Nippon ก่อน ต้นทุน 0 บาท**
- ⚠️ **คำถามที่ยังไม่ได้คำตอบ:** รายการวัตถุดิบ 15 รายการ**ไม่มีแม่สี (tinter) แยกตัว** → toun อาจ**สั่งสีผสมสำเร็จตามเบอร์** ไม่ได้ผสมเอง ถ้าใช่ เรื่องเครื่องชั่งตกไปทั้งหมด **ควรถามให้ชัดก่อนทำอะไรต่อ**

## 9. วิธีทำงานกับโปรเจคนี้ (บทเรียนจาก session นี้)

**เครื่องมือ**
- Supabase ต่อผ่าน **MCP เท่านั้น** — `curl` จาก sandbox ถูกบล็อก (HTTP 000)

- ทดสอบ UI ด้วย **Playwright + mock Supabase** (`page.route` ดัก `.supabase.co`) — ได้ผลจริงโดยไม่แตะข้อมูล production

**กฎที่ต้องระวัง**
- เขียน commit message **อย่าใช้ backtick** — shell จะตีความเป็นคำสั่ง (เจอมาแล้ว) ใช้ `git commit -F -` แทน
- แก้ไฟล์ที่ถูก cache (`stock.html`/`erp.html`/`po-*.html`) **ต้อง bump `CACHE_NAME` ใน sw.js**
- ก่อน merge เข้า main ตรวจว่าไฟล์ PO เดิมไม่ถูกแตะ:
  ```bash
  git diff --stat <prev>..main -- po-mobile.html po-desktop.html index.html manifest.json
  # ต้องว่าง
  ```
- Playwright: ปิด modal ก่อนกดปุ่มอื่น ไม่งั้น backdrop จะบัง
